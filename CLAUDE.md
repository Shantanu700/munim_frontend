## Design context

`PRODUCT.md` and `DESIGN.md` at the repo root are the strategic and visual source of truth for
this app, read by `/impeccable` before any design work. Short version: Munim is a trust-and-
visibility layer for agentic commerce — it lets a merchant's store transact safely with AI shopping
agents (policy gate, audit ledger) and be discoverable to them (agent-readable catalogue, MCP
endpoint). Register is `product` (dashboard, not marketing), platform is `web`. Primary user is the
merchant; a `buyer` role exists at signup but has no dashboard yet — future scope, not built. Brand
personality: trustworthy, precise, in-control — explain the reason, never just the verdict, and
never lean on color alone. See `PRODUCT.md` for the full brief and `DESIGN.md` for tokens/rules.

## Commands

```bash
bun dev      # dev server (also regenerates AGENTS.md and .next/dev/types/*)
bun build
bun start
bun lint     # bare `eslint` — no path args, config in eslint.config.mjs
```

Bun is the package manager (`bun.lock`, `@types/bun`). A stale `package-lock.json` is also
committed; ignore it, don't feed it. No test runner is configured — there is nothing to run
and nothing to add unless asked.

Adding UI components: `bunx shadcn@latest add <name>` — it respects `components.json`
(style `base-luma`, baseColor `mist`) and writes into `components/ui/`.

## Stack facts that will bite you

- **Next.js 16 + React 19.** See `AGENTS.md`: read `node_modules/next/dist/docs/` before
  writing framework code, since conventions differ from older Next.
- **Route props come from generated types.** `app/layout.tsx` uses the global
  `LayoutProps<"/">` (not a hand-written `{ children }` type). These globals live in
  `.next/dev/types/routes.d.ts`, generated by `next dev` — typecheck fails on a clean
  checkout until the dev server has run once.
- **shadcn/ui here is Radix-based**, style `radix-luma` in `components.json`. Components
  import from the unified `radix-ui` package (not individual `@radix-ui/*` scopes), and
  compose with `asChild` + `Slot`. Adding a component pulls the matching `radix-luma`
  variant automatically, so don't paste Base UI or `@radix-ui/react-*` snippets.
- **`data-open:` / `data-closed:` are shadcn custom variants**, defined in
  `shadcn/tailwind.css` to match *both* `[data-state=open]` (Radix) and `[data-open]`
  (Base UI). Prefer them over hand-written `data-[state=open]:`.
- **Tailwind v4, CSS-first.** No `tailwind.config.*` exists and none should be created.
  Theme lives entirely in `app/globals.css` via `@theme inline` + `:root`/`.dark` custom
  properties (oklch). Radii derive from a single `--radius`.
- `@/*` maps to the repo root, so `@/components`, `@/lib`, `@/hooks`.

## State of the app

Twelve routes. `/` redirects to `/dashboard` and `/auth` is the login/register screen; the
merchant has seven under `/dashboard` — the Overview, `orders` (the orders list), `products`
(the catalogue), `ledger` (the audit ledger), `policy` (the store policy editor),
`razorpay` (the payout screen) and `webhooks` (the webhook-hit log) — and the buyer has three
under `/buyer`, covered in *The buyer area*. Everything below this line describes the merchant side unless it says otherwise.

`app/dashboard/layout.tsx` is the auth guard. It has to be a client component — the
`sessionid` cookie belongs to the API origin, so Next middleware cannot see it and
`GET /core/login/` is the only way to ask whether a session is live. It renders `null`
until that resolves, redirects to `/auth` on 401, and passes the `Login` object to both
`AppSidebar` and `Topbar`. It also puts that object on `SessionContext`
(`components/dashboard/session.tsx`) for the screens below. That context was kept through a
period with no consumers "because a screen needing the signed-in user is one route away" —
and it now has two, both wanting the same field: the ledger screen reads
`merchant?.domain` for `/audit/verify?merchant=…` and the printed public GET line, and
`ExportChainButton` reads it for the download filename. `useSession()` throws instead of
returning `null`, which is safe because the layout renders nothing until the fetch resolves.
`merchant` itself is `Merchant | null` (a buyer has none) **and `domain` is optional on top
of that**, so it needs `?.` and a `??`/`||` fallback both.

The layout also owns `components/dashboard/topbar.tsx` — search, the agent-traffic switch,
the theme toggle, the account block — so every screen under `/dashboard` gets the same
header. A page arrives as that client layout's `children` and is therefore still a **server**
component, which is why `app/dashboard/page.tsx` can `await searchParams` instead of
reaching for `useSearchParams` and a Suspense boundary.

The rail is `variant="floating"` — the design draws it as a rounded `--panel` inset from
the page, not a flush full-height column. `p-panel` on it overrides the variant's default
8px, and `md:pl-0` on the content wrapper stops the two paddings stacking, so the gap either
side stays the mandated 6px. `sidebar.tsx`'s floating styles were edited once to swap
`shadow-sm` for `shadow-card` and drop the ring; `rounded-2xl` needed nothing, since the
theme already clamps it to the 32px ceiling.

`components/app-sidebar.tsx` is now Munim's own rail: a Menu group (Overview, Orders,
Products, Ledger, Policy) and a General group (Webhook responses, Razorpay settings, Settings,
Help), with lucide icons and `usePathname()` driving the active navy pill. Everything in Menu
has a route now, plus Webhook responses and Razorpay settings; Settings and Help are still `#`. Orders' badge is
`GET /orders/counts`'s `by_status.needs_attention`, fetched in the component and silent on
failure, so the rail cannot contradict the "Needs attention" pill on the screen it links to —
and it is hidden at 0, since a badge reading zero sends a merchant looking for work that is
not there. `NAV` is a plain list and the badge is matched by route (`ORDERS`), because it is
the only item with a live count. shadcn's sample data is gone, and with it
`nav-main.tsx`, `nav-projects.tsx` and `team-switcher.tsx` — flat items need none of their
collapsible/dropdown machinery. `nav-user.tsx` survives because it holds the real
`DELETE /core/login/` wiring (its Upgrade/Billing/Notifications items are still fake).

`components/dashboard/kill-switch.tsx` sits in the rail's footer: the navy card from the
design when expanded, and a single `SidebarMenuButton` when collapsed so the icon lands on
the same centre as the nav. It branches on `useSidebar().state` in **JS, not CSS** — two
`hidden`-toggled `PopoverTrigger`s would both register as the popover's anchor and the one
without a layout box would win. Confirming just toggles and closes — the layout owns the
request and every toast about it, because announcing success here would celebrate a change
the PUT can still reverse.

`agentsOn` is the one piece of shared dashboard state. The topbar switch and the kill switch
are the same boolean, so it lives in `app/dashboard/layout.tsx` and reaches both as props —
the layout renders both consumers, so a context would buy nothing.

It is **real now**: `PUT /policy/kill-switch/` arms and disarms the gate store-wide, and the
layout writes it optimistically (this is the one control a merchant may be reaching for in a
hurry, so it must not wait on a round trip) and rolls back on failure. `GET /policy/overview/`
is the *only* endpoint reporting the current position — `Login.merchant` does not carry it —
so the layout fetches it alongside the auth guard, separately, because it 404s for a buyer and
must never be able to bounce a good session. Deliberately not a policy rule: it has to work
when the store has no active policy, which is exactly when a merchant most wants it.

`hooks/use-mobile.ts` (shadcn's, untouched) fails `bun lint` on
`react-hooks/set-state-in-effect`. Pre-existing, but the sidebar pulls it onto the render
path, so `bun lint` is not green. That one error plus an `import/no-anonymous-default-export`
warning on `openapi-ts.config.ts` are the whole of the expected output — anything else is new.

## Dashboard data is mock

`lib/dashboard-data.ts` holds what is left of the Overview screen's figures, ported from the
design project's `Munim Dashboard.dc.html`. It is mock **because the API has nothing to
fetch**: no store, payments or catalogue-traffic endpoint exists. Replace each export with a
real call as the endpoints land; the shapes are the intended contract.

Products, policy, the ledger and orders are the exceptions and no longer live here — see
*The Products screen*, *The policy screen*, *The audit ledger* and *The Orders screen*. What
remains of the policy exports is copy, not data: the breach sentences and the enforcement
mapping, which the wire does not carry.

**`components/dashboard/overview.tsx` is a client component**, and has to be: the `sessionid`
cookie belongs to the API origin, so nothing rendered on the server can ask the orders
endpoints anything. `useOrdersPreview()` feeds both the Orders tile and the Orders panel,
which sit in two different grids — two islands would make the same two requests twice. It
returns `null` while that resolves rather than guessing `live` for one paint, which is the
same thing the dashboard layout above it does with auth. `GatePanel` is no longer an island
in a server screen, just a child that owns its own fetch.

Two consequences worth knowing:

- **`?empty=1` on `/dashboard`** forces `storeSummary` to `null` and renders the "store
  details not entered yet" empty state. Nothing in the API reports store setup, so a URL
  param stands in for the check. It is the one line to swap when a store endpoint exists.
  The page stays a server component for it.
- **The day-one empty state** (S2b in the design — gate armed, zero orders) is no longer a
  fixture switch: it renders when the store's order total is 0, which is what it always meant.

`bars()` / `linePoints()` in the same module are the chart geometry, copied from the design
file's `renderVals()` against a `0 0 640 180` viewBox. Both charts are inline SVG — there is
no charting library here and none is needed.

## The Orders screen

`/dashboard/orders` is S2 minus its mock, and it is **fully live** — the fifth such screen.
`hooks/use-orders.ts` owns the whole flow. Five endpoints, all under `/orders/`, and three of
them disagree about which filters they honour **on purpose**: the list takes `status` and `q`,
`counts` takes `q` but *is* the status breakdown so it ignores `status`, and `tiles` ignores
everything — a KPI is a fact about the store, not about whichever tab is open.

Four things about that backend the screen is built around:

- **Cursor pagination, not page numbers.** `{results, next_cursor, has_more, total}`. The list
  grows at the head, so an order placed between two scrolls would shift every offset and the
  reader would see one row twice and miss another. Two traps follow. `total` comes back **only
  on the request that arrived without a cursor** and is `null` on every later page, meaning
  *unchanged* — writing it through blanks the count line the moment a merchant scrolls, so the
  hook only assigns it when it is not null. And `LoadMore` is gated on `has_more`, never on
  `count - rows.length`.
- **`awaiting` is not a status.** `?status=` takes `all|paid|pending|failed|expired|needs_attention`.
  `counts.tabs` carries `source`: `"orders"` means the key is a valid `?status=` value,
  `"step_ups"` means it is not — those rows are the approvals surface's, not this list's, so a
  pill for one would filter to nothing. The pills are therefore `tabs.filter(source ===
  "orders")` with "All" prepended off `orders_total`. For the same reason the "Awaiting
  approval" tile has to say **step-ups** waiting on a human: it is a different table from
  orders waiting on a card, and "orders" there would be a number the list cannot show.
- **`agent_label` is self-declared** — read from User-Agent and Origin at checkout, both
  trivially spoofable. It is attribution for a dashboard, never an authenticated identity, and
  the rail says so in a line under the facts. Blank renders as "not stated", not as an empty
  cell.
- **Rows are addressed by `uuid`**, never `order_number`, which is per-tenant and sequential
  and therefore enumerable. Selection and React keys use the uuid; `order_number` is only
  printed, with `uuid.slice(0, 8)` behind it since it is optional on the wire.

The rest:

- **`OrderStatusPill` takes a bare `string`**, like `VerdictPill` and for the same reason:
  `OrderRow.status` is *optional* on the wire, and a total `Record<Status04aEnum, …>`
  destructuring `undefined` is exactly the crash the ledger's table hit on its first `CONFIG`
  row. The fallback carries no status colour, so §1 rule 2 holds.
- **Search is `?q=`** over order number, product, buyer, Razorpay ids and reason codes,
  debounced 300ms. The input holds `q`; the request uses `query`, a beat behind. A `setTimeout`
  callback clears `react-hooks/set-state-in-effect` the same way a `.then` boundary does. The
  topbar's search box is decorative and belongs to the layout — this is a second, real one.
- **Filters are part of the request.** A pill click or a new search resets the cursor;
  filtering only the loaded pages would print "Paid 123" beside twenty visible rows. A
  `generation` ref discards a page that lands after the filter moved on.
- **Timestamps arrive ISO-8601 and are formatted here** — the client knows the reader's
  timezone where the server only knows the merchant's. `moment()` in `parts.tsx` does it.
- The table is products' **container-query** table (`@[42.5rem]`, five columns, one DOM), not
  the ledger's `min-w-195` horizontal scroll — this panel is much wider at xl, where the detail
  rail sits beside it, than at lg. Status sits before agent in the DOM (card reading order,
  since status is what a merchant scans for) and `@[42.5rem]:order-*` puts it back last.
- Row selection and the detail rail are the ledger's inspector pattern, including the fallback
  to `rows[0]` when the filter excludes the selected row, and the `detail?.uuid === order?.uuid`
  guard that replaces a clearing setState in the effect. `GET /orders/{uuid}` is a second call
  the rail cannot avoid: `product_url`, `unit_price_paise`, `reference_id` and the two reason
  sentences are on no list row. Both `failure_reason_description` and
  `step_up_reason_description` are **blank in the ordinary case** — an order exists only on an
  ALLOW — so they are skipped rather than rendered empty, the ledger's rule again. The
  storefront link lives in the rail because a list row is a `RowButton` and may hold no link.
- **"See the decision behind it" is built from `decision_seq`**, not `decision_url`: that field
  is an API path, not a route on this dashboard. It links to `/dashboard/ledger?seq=N`.
- `ExportButton` takes the **thunk** form and hits `GET /orders/export`, which honours the
  active status and search — so the button can honestly offer the whole filtered set rather than
  the pages already scrolled past. Unlike the ledger's export it caps: `truncated` is warned
  about out loud, since a short file with no notice is worse than a refusal. Still JSON rather
  than the design's "Export CSV" — the endpoint answers JSON and nothing here needs a serialiser.

## The Products screen

`/dashboard/products` is S1a from `Munim Screens.dc.html` minus its onboarding stepper: the
scan controls and the catalogue they produce, on one screen. Scanning deliberately has no tab
of its own — its only output is that table, so splitting them would mean acting on one screen
and reading the result on another.

**It is fully live** — the first of three, now, with policy and Razorpay. Every figure comes
from the API, so unlike the mock screens it is a client component end to end and has no
`?empty=1`: its empty states are
real conditions, not a URL param.

`hooks/use-ingest.ts` owns the whole flow and is the only place to change it:

- `GET /ingest/` on mount returns the merchant's `domain`, `mcp_url` **and** the in-flight job
  if there is one. It no longer carries products. Between it and `GET /ingest/products` the
  screen has everything it needs, which is why the page needs no session context and
  `app/dashboard/layout.tsx` was left alone.
- `GET /ingest/products` is the catalogue: paginated, `{count, next, previous, results}`, at
  `page_size` 20, and the list pages itself on scroll — `components/dashboard/load-more.tsx`
  is the sentinel at its foot, shared with the orders screen, whose `IntersectionObserver` is
  torn down while `busy` and rebuilt after, so a page too short to overflow the scroller still
  triggers the next one (an observer only fires on *changes*). The two mount requests are deliberately *not*
  `Promise.all`'d — `/ingest/` 404s for a buyer or for a merchant row that was never created,
  and that must not blank a product list which loaded perfectly well.
- `POST /ingest/` takes `{source, match?, limit?}`. It is idempotent while a job is
  PENDING/RUNNING — the view returns the existing job — so a double submit cannot start two
  crawls. `domain`/`business_name` are not exposed in the form: the backend infers both from
  the source URL's host.
- `GET /ingest/{job}/stream` is SSE. `new EventSource(API_BASE + stream_url, { withCredentials:
  true })` — `withCredentials` is EventSource's own flag and `lib/api.ts`'s
  `credentials: "include"` does **not** reach it. Named events only: `progress`, `product`,
  `done`, `error`.

Two traps in that stream. Its `error` event is **two** different failures sharing one name —
a `MessageEvent` carrying data means the job failed and the message is written for a merchant
to read; no data means the socket dropped and says nothing about the job. And rows are
deduplicated by **`uuid`** — the identity the API addresses a row by, and the key its edit and
delete need. Never by `sku`, which is blank on any page that published none, and no longer by
`url`, which the list `Product` shape does not carry.

The design's staged reveal is now real rather than simulated: the bar in
`components/dashboard/scan-panel.tsx` tracks the job's own `processed`/`total`, and the rows
beside it arrive on the same stream that moves it. Nothing advances on a timer.

That only works because the backend publishes a `status` event on every save that changes
something visible — `PROGRESS_FIELDS` in `twin/signals.py` is `{job_status, total_urls,
processed}`. Gating on `job_status` alone (as it originally did) fires on exactly two saves,
so the client sees `0/0` at connect and then the finished totals: a bar that is only ever
empty or full. If progress ever freezes again, check that set first.

A rescan emits no `product` events for products that already exist — the backend signal fires
on create only, to stay aligned with `created_count`. That is why the table is hydrated from
`GET /ingest/products` first and the stream only adds to it, and why the `done` handler
refetches page one: an updated price reaches the table by no other route. That refetch drops
any extra pages the merchant had loaded, which is honest — the ordering just changed.

## Products CRUD

The merchant owns the catalogue, not just the scan: `POST /ingest/products`,
`PUT /ingest/products/{uuid}` (partial, so flipping `is_visible_to_agents` cannot clobber the
other columns) and `DELETE`. All three live in `use-ingest.ts` beside the stream, since they
mutate the same list. None is optimistic — create and update both return the saved row, so the
table shows what the server stored rather than what the form guessed, and each returns a
boolean because the dialog only closes on a write that actually happened.

`components/dashboard/product-dialog.tsx` is the one editor, add and edit alike. Three things
about it:

- **It is mounted only while open and keyed `uuid ?? "new"`.** That remount is what resets the
  form, the fetched detail and an armed delete. Do not replace it with a reset effect —
  `react-hooks/set-state-in-effect` is an *error* in this repo, so a synchronous setState in an
  effect body breaks `bun lint`. `use-ingest.ts`'s `load()` is a `.then` chain rather than
  async/await for exactly the same reason: an `await` does not clear that rule, a `.then`
  boundary does.
- **Editing fetches `GET /ingest/products/{uuid}` first.** A catalogue row cannot prefill the
  form: `url` and `is_visible_to_agents` are on `ProductDetail` only, and a form that posted
  defaults for fields it could not see would silently clear them.
- **Rupees in, paise stored**, and the `Math.round` is load-bearing — `4200.1 * 100` is
  `420010.00000000006` and the column is an integer. `in_stock` is a three-option `<select>`
  where blank means `null`; the same tri-state rule as the meter applies, so never coerce it.

The catalogue row is a `RowButton` (`parts.tsx`) — a real `<button>`, so focus and keyboard
come free — which means it may contain no link. That is why the storefront URL moved into the
dialog rather than staying on the title.

**Layout, and one trap.** The rail splits off at `lg`; only at `xl` is the page pinned to the
viewport with its panels sized by flex. The catalogue list scrolls inside its card at every
width — below xl a `max-h-120` supplies that height, and `xl:max-h-none` hands it back to
`flex-1` once the page is pinned. Every `min-h-0` on this screen is `xl:min-h-0` — never bare. The page grid is a flex item inside the layout's `overflow-y-auto`
column, so a bare `min-h-0` lets it shrink to the scroller's height at *every* width; below
xl nothing scrolls internally, so the grid's rows get squeezed and the product rows paint
straight over the rail beneath them. It looks like a stacking bug and is really a flex one.

The catalogue itself switches between the five-column table and stacked cards on a
**container** query (`@[42.5rem]`, the 680px the columns need), not a media query: the same
panel is ~800px wide at xl but ~600px at lg, so a viewport breakpoint is wrong at one of the
two. One DOM serves both — rows are `flex-wrap` when narrow and become the grid above the
threshold, with `@[42.5rem]:order-*` restoring the column order.

The six-bar meter is derived in `detailsFor()` (`components/dashboard/parts.tsx`), not sent by
the API. `Product.in_stock` is **nullable and three-valued**: `null` is "the page published no
availability" and fills no bar, `false` is a published "out of stock" and does fill it. So the
check is `!== null`, never `Boolean()` — and the backend must not coerce on the way in either
(`tasks.py` writes `item.in_stock`, not `bool(...)`).

## The audit ledger

`/dashboard/ledger` is S2c, reached from the sidebar, from Overview's "Open ledger →" and from
an order's "See decision N", and it is now **fully live** — the fourth such screen.
`hooks/use-audit.ts` owns the whole flow.

**`?seq=` opens one entry**, which is what the orders screen links to. That is why the route
splits: `app/dashboard/ledger/page.tsx` is a small **server** component that awaits
`searchParams` and renders `components/dashboard/ledger.tsx`, the same trick
`app/dashboard/page.tsx` documents for `?empty=1` — a page arrives as the client layout's
`children` and is still rendered on the server, so `useSearchParams` and its Suspense boundary
are not needed. `Number(...) || undefined` means a `?seq=` that is unparseable, or 0 (the chain
starts at 1), falls through to the ordinary newest-first screen rather than erroring.

Two things that link needs. `useAudit(domain, seq)` seeds `selected` with it, and the
`rows[0]` fallback is skipped **only for that seq** (`selected === seq`): a decision can sit
thousands of entries below the loaded pages, and quietly showing entry one instead would answer
"what allowed this order?" with an unrelated entry. A row the *filter* excludes still falls
back, as the inspector always has. The rail then draws from `entry ?? position`, which works
because `LedgerEntryDetail` is a **superset** of `LedgerEntry` — the linked entry needs no
paging to reach, just its own fetch, and the rail says it came from a link.
Four endpoints, served by the backend's `ledger` app under the `audit/` prefix (there is no
app called `audit`, and the four URLs carry **no trailing slash**, unlike `core/` and
`policy/`).

Four things about that backend the generated types cannot tell you, each of which decided
something here:

- **A broken chain is HTTP `409`, not `200 {ok:false}`.** `GetAuditVerifyResponses` types only
  the 200, so a break arrives in `error` — the page's old `data?.ok` branch was unreachable.
  `chainOf()` in the hook parses `data ?? error` through one path for that reason. This is the
  *opposite* of the Razorpay convention (`201 {ok:false}`), so do not "make it consistent".
  A break must also never reach `describeApiError`, which would walk the nested payload and
  print the bare string `prev_hash mismatch` at a merchant.
- **`decision` is not the three verdicts.** Policy edits and Razorpay writes append to the
  same chain with `decision="CONFIG"` — on a real dev database that was *eight of seventeen
  rows*. `VerdictPill` therefore takes a bare `string` with a neutral fallback; the old total
  `Record<Verdict, …>` destructured `undefined` and crashed the table. There is no
  server-side "verdicts only" filter (`?decision=` takes only the three), so these rows
  cannot be filtered out without lying about `count` and breaking the paging.
- **`agent` / `buyer_uuid` / `buyer_label` are `""`, never null** — the view coerces with
  `detail.get(…) or ""`. So `||`, never `??`. And blank does not mean one thing, which is
  what `callerOf()` in `parts.tsx` exists for: on a `checkout` a blank agent is the engine's
  "no valid mandate was presented", but on a `policy_change` or `razorpay_*` row it means the
  merchant did it from this dashboard, where "unsigned caller" would read as an intrusion. The
  actor is in the `detail` blob (`actor_email`, `by_user`) and the inspector prints it there.
- **`reason_description` is blank for most codes, by design.** `describe()` in the backend's
  `reasons.py` covers the gate's verdicts only and returns `""` for anything else *on
  purpose* — "entries are permanent and codes are not". Every row on a fresh install has an
  empty one. Both the rail and the gate panel therefore skip the element rather than render an
  empty one with its margin. Do not treat a blank as a bug to fill in.

`GET /audit/entries` is paginated on `seq` descending (gapless per tenant, so a page boundary
cannot duplicate or skip the way two rows sharing a timestamp can), `page_size` **max 50**.
`GET /audit/entries/{seq}` is a second call the rail cannot avoid: `prev_hash` and the raw
`detail` blob are on no list row. It is fetched per selection and the response is matched by
its own `seq` before rendering — that check is what replaces a clearing setState in the
effect, which would be a lint *error* here. The blob is printed key by key, snake_case, with
`*_paise` through `rupees()`: the keys differ per action and every one is optional, so a
hand-written label map would need a frontend release for each key the engine learns to write.

`GET /audit/export` is unpaginated and unfiltered on purpose — a partial chain cannot be
verified — so it is fetched at click time and never held in state.
`components/dashboard/export-chain.tsx` is that button, and it exists as its own component
because **Overview is a server component and a fetching thunk cannot cross that boundary as a
prop**. `ExportButton` grew a thunk form for it (`data: unknown | (() => Promise<unknown>)`);
a `undefined` result means the fetch failed and already toasted. It stayed a download rather
than becoming a plain link to the endpoint, which its old comment predicted: the `sessionid`
cookie belongs to the API origin, so a link is a cross-origin navigation whose auth depends on
the browser's SameSite treatment.

`GET /audit/verify` is the only unauthenticated endpoint in the project. It is checked once on
mount **silently** — a page load must not announce a result nobody asked for — and the pill
under the printed GET line is where that check reports. Clicks toast; the mount check does
not, which is why `check(id?)` takes the `toast.loading` handle as its only argument. Two
traps in its payload: `?merchant=` matching nothing returns `{ok: true, merchants: {}}`
(Python's `all([])`), which is a proof of nothing and must not read as verified; and the
per-tenant object has two shapes, `{ok, verified, head}` or
`{ok: false, broken_at_seq, error, verified}`, where `verified` then counts the entries that
checked out *before* the break.

**Overview's gate panel** (`components/dashboard/gate-panel.tsx`) reads the same endpoint and
is a client island precisely because `overview.tsx` is a server component. It costs **four
reads for three counts** — a `page_size: 1` response fetched purely for its `count`, once per
verdict — because no aggregate endpoint exists and `Tiles` carries only `refused_30d` /
`step_ups_30d`: no ALLOW count, and the wrong window. `Promise.all` is right here where the
policy screen's rule writes are sequential; it is *writes* that queue on `LedgerEntry.append`'s
row lock. Two things follow from the counts being all-time: the panel **dropped "· last 24
hours"** from its heading, and its three tallies are printed as three facts rather than a
breakdown of the total, which they cannot sum to while `CONFIG` rows share the chain.

Two shared pieces moved into `parts.tsx` for this work: `callerOf()` (above) and `moment()`,
an ISO timestamp as a merchant reads it — promoted out of `razorpay/page.tsx`, which was the
only date formatter in the repo and was module-private.

**Product images.** `ProductThumb` renders a plain `<img>`, not `next/image`, on purpose:
these URLs come from whatever domain the merchant's storefront lives on, so optimising them
would need a wildcard `remotePatterns` — an open image proxy on our own origin. The fallback
icon is always in the box with the image layered over it, and `onError` hides the image, so a
404 shows the same faint square as a product that published no URL. Do not "simplify" that
back into a ternary: stores really do publish image refs that resolve nowhere, and a
broken-image glyph in every row reads as our bug rather than their markup.

## The policy screen

`/dashboard/policy` is S2e, and it is now **fully live** — it was the most thoroughly mock
screen in the app until the policy API landed. `hooks/use-policy.ts` owns the whole flow;
what is left in `lib/dashboard-data.ts` is only the copy the wire does not carry
(`ENFORCEMENTS`, `enforcementOf`, the `BREACH` templates, `ruleSentence`).

**Two endpoints carry the screen, and the third and fourth are traps.** `GET /policy/overview/`
is one call *by design* — tiles, cards and `active_policy` describe the same moment, and
assembling them from separate requests lets a total disagree with the rows under it.
`GET /policy/policies/{uuid}/` **seeds missing rule rows on read**, so it always answers with
every kind the backend knows. That is why nothing calls `getPolicyRuleCatalog` or
`getPolicyRule`: each `Rule` already carries its own `label`, `description` and
`config_fields`. `getPolicyPolicies` is likewise redundant — the overview has the list.

- **Rules are addressed by `kind`, never uuid**, and written one at a time through
  `PUT …/rules/{kind}/`. `PolicyWrite` is `{name}` only, so one Save fans out to N rule PUTs —
  sequential, because every write appends to the money chain and `LedgerEntry.append` locks
  the merchant row to advance the sequence. `Promise.all` would only queue on that lock.
- **Edits are a patch map, not a copy plus a baseline.** `pending: Partial<Record<KindEnum,
  RuleWrite>>` in `PolicyEditor` *is* the request list, and `RuleWrite` is partial by design.
  A field the merchant never touched is never sent, which is load-bearing: a stored ceiling of
  ₹123.45 shows as ₹123, and echoing every field back would quietly round it down. `patch()`
  drops anything equal to what the server holds, so an edit and its undo leave nothing behind.
- **Enforcement is four pills over two wire fields.** `Refuse`/`Ask the buyer`/`Ask you` set
  `{state:'enforcing', on_breach:…}`; `Off` sets `{state:'off'}` and leaves `on_breach` alone.
  There is no "Log only" — `draft` evaluates nothing, and `choices.py` names that overload as
  the one to resist. `ask_merchant` must stay offered: it is the *default* for
  `per_order_ceiling` and `min_catalog_confidence`. A seeded rule reads `draft` while **Off**
  is lit, so `patch()` compares the *pill*, not raw `state` — writing `off` over `draft` would
  be a real transition with a ledger entry, for a click that changed nothing.
- **The config form is generic**, built from each rule's `config_fields` (shape declared by
  hand in `page.tsx`; `types.gen.ts` has it as an untyped dict). Three widgets cover all eight
  kinds: choice pills, a comma-separated list, and a number. The `UNITS` map is keyed by field
  *name* and is the one thing breaking the backend's "a new kind needs no frontend release"
  promise — a descriptor says `integer, min 1, nullable`, never *paise*. An unknown kind still
  renders and writes, just in raw storage units.
- **Blank is not zero.** `amount_paise` is nullable and `null` means *no limit*; a `0` would
  refuse every order in the store. Non-nullable numerics coerce blank to `min_value ?? 0`,
  never `null`. Clamping happens **after** unit conversion, since the bounds are in storage units.
- `config_valid === false` means the stored config cannot be evaluated — the engine fails it
  open, so the rule reads as enforcing and refuses nothing. Surfaced per rule in words with no
  colour: `--step` is for verdicts, and colour never carries meaning alone (DESIGN.md §1 rule 2).
- **`updated_at` never moves.** Every write in the backend's `services.py` uses
  `QuerySet.update()`, which skips `auto_now`. Provenance comes from `getPolicyHistory` and
  `tiles.last_change_*`, never from `policy.updated_at`.
- `price_change_tolerance` is the odd rule: `on_breach=refuse` is a no-op (`_price_drift_in_band`
  returns `None` — "keep refusing, which already happens") and it can never widen to ALLOW. Its
  sentence says so rather than the pills special-casing it.
- `PolicyEditor` is keyed on the policy uuid, so switching discards edits by remounting. Same
  trick as `ProductDialog`, same reason: a reset effect is a synchronous setState in an effect
  body, which is a lint *error* here. `use-policy.ts`'s effects are `.then` chains for the same
  reason, and the detail effect has **no clearing branch** — the page renders the editor only
  when `uuid` is set, so a leftover detail is unreachable.
- The value field is a text input, not `type="number"` — `₹1,50,000` without its grouping is
  unreadable, and grouping is a rendering of a number the state still holds (digits are
  stripped on the way in). The policy cards are `aria-pressed` buttons, matching the ledger's
  filter pills rather than hand-rolling `role="radio"` keyboard semantics.
- `is_active` + `overview.active_policy` replaced the mock's tri-state `status`, and they drive
  **logic only** — which policy is in force, whether Delete is available, what the rules panel
  says. No badge: the IN FORCE / STANDBY / DRAFT tags were removed on request and the line
  under "Choose the policy in force" names the live one. Don't reintroduce them.
- `active_policy` can legitimately be `null`, which means **no store rules apply at all** — a
  real state ("Run no policy"), not an absence. The mock's `inForce ?? policies[0]` survives
  only as the *default selection*, never as the answer to what is in force.

## The Razorpay screen

`/dashboard/razorpay` is S2d, minus the design's onboarding stepper (Products dropped its
stepper for the same reason). Heading conventions come from the other three screens: an `h1
.text-page-title` with a one-line `p.text-body.text-muted-ink` under it, outside any panel, in
`px-1.5 py-1`; a status strip below it the way the ledger puts its filter row there; then the
`lg`/`xl` two-column grid Products uses. Card headers are `text-card-title` — the design draws
"Connect your Razorpay account" at headline size only because it has no page title of its own.

**It is live now**, and every one of the three "deliberately fake" constructs this section used
to document — a disabled key fieldset, a webhook-secret box that printed nothing, a test-event
button that was an outbound link — is gone, because each of them now has an endpoint.
`hooks/use-razorpay.ts` owns the whole flow.

`GET /core/razorpay/` is one call by design: keys, webhook address, subscribed events and the
last event received describe the same moment, and fetching them separately lets the status pill
disagree with the boxes under it. It is also the only source for `key_secret_set`, `key_mode`,
`verified_at`, `account_name` and `webhook_received` — so the screen **no longer reads
`SessionContext`**. `Login.merchant` answers two of the sixteen fields it draws, both `readonly`
with no setter in sight, which means a saved key would leave the session's copy stale with no
way to correct it. `useSession()`'s consumers are now the ledger screen and
`ExportChainButton`, both of which want only `merchant?.domain` — not this screen.

- **Two buttons, by request: Save stores, Verify asks Razorpay.** `PUT /core/razorpay/` is
  partial, so a merchant fixing a typo in a key id gets it on file without spending a round
  trip. The cost of that choice is real and worth knowing: a secret Razorpay would reject can
  sit in storage until someone presses Verify, and a later key-id-only PUT re-pairs with it.
  The save toast says so ("Verify the pair to confirm Razorpay accepts it"). If that trade ever
  bites, the fix is to chain verify before the PUT inside `save`, not to add a fourth button.
- **A rejected key is `201 {ok: false}`, not a 4xx.** Both `POST …/verify/` and
  `POST …/test-event/` answer that way, so `data` is truthy on failure and `!data.ok` is its
  own branch. Collapsing it into the `!data` transport branch reports "Something went wrong"
  for a wrong key — and `describeApiError` must never be reached for one of these, because the
  body carries Razorpay's own sentence, which beats anything the client could invent.
- **Only the PUT returns fresh state.** Verify and mint answer with their own shapes, so
  `verified_at`, `is_payment_ready`, `account_name` and `webhook_received` move by refetch.
  Every action but `save` therefore ends in `refresh()`.
- **An empty verify body is meaningful**, not a bug to guard: it re-checks the pair already on
  file. `creds()` keeps only non-empty fields, which is what lets one builder serve a first
  save, a key-id correction, and a bare re-verify.
- **`pattern="rzp_…"` on the key-id input is load-bearing.** That value reaches
  `LedgerEntry.detail`, which is append-only, so the shape check is what stops a secret pasted
  into the wrong box from becoming a permanent row. Deliberately looser than the backend's own
  regex — guessing that exactly risks refusing a valid key in the browser.
- **Munim mints the webhook secret and the merchant may also paste their own.** The mint button
  is in the dark panel; the paste path is a third optional field in the left-hand form, because
  the PUT takes all three credentials in one body and a second form would need its own submit
  and busy state. Minting *over* an existing secret goes behind a Popover confirm — `replaced`
  means a webhook already configured in Razorpay silently stops verifying — and the hook warns
  on `replaced` regardless, since another tab may have minted one.
- **The test event is ours and signed**, so `last_event_was_test` has to stay named on screen:
  a merchant who has only received Munim's own test event has not proven Razorpay is
  configured, and a bare "last event: payment.captured" would tell them they had.
- **The field hints live in a `?` beside each label**, not under the input: three sentences of
  where-to-find-this made the form more prose than form. It is `components/ui/tooltip.tsx`
  (already installed, and `SidebarProvider` already mounts the `TooltipProvider` the whole
  dashboard sits in), so it opens on hover *and* on keyboard focus — which is why the trigger
  is a real `<button>` with an `aria-label` and why `Field` associates its label with
  `htmlFor` instead of wrapping the input: a button inside a `<label>` activates that label's
  control on every click.
- **`busy` is one tagged string** (`"save" | "verify" | "secret" | "test"`), not four booleans —
  it labels the button that is working and disables the other three, and four booleans are four
  states that can disagree.
- The status pill is five ordered branches naming the *first* outstanding step, so it always
  matches the next button to press. `is_payment_ready` is the server's own answer and outranks
  every gate below it. No `bg-deny-tint` anywhere here: an unfinished setup is a step, not a
  refusal. `source` ("accounts" vs "probe") stays in verify's toast — it is on no GET, so
  showing it would mean holding the last verify response purely to print one line.
- **Verification is state, not just a toast.** The pill's `!verifiedAt` branch and the pill
  beside the Save/Verify buttons are the only things that report Razorpay's own verdict, and
  they must not be collapsed into `is_payment_ready`: a store with a verified pair and no
  webhook yet is not ready, and used to read as if nothing had been verified at all. Trusting
  `verified_at` for that claim is safe because the backend earns it — `save_credentials`
  clears it when either key changes, and `verify_and_record` sets it only when the pair
  checked *is* the pair on file, so verifying an unsaved pair still reads unverified however
  cheerful verify's toast was.

## The webhook responses screen

`/dashboard/webhooks` replaced the rail's dead "Payouts" item. One file,
`app/dashboard/webhooks/page.tsx`, with its fetch inline — one consumer, so no hook module.
`GET /webhooks/hits` is **page-numbered** (`{count, next, previous, results}`, `page_size`
default 10 / max 50), not cursor-paginated like orders, so `LoadMore` is gated on
`rows.length < count`. Three things it holds to: `signature_valid` is nullable and
three-valued — `null` is "no check was made", which is not the claim a failed check makes —
`event_type` / `razorpay_event_id` are optional and blank reads as "not stated", and
`error_detail` is blank in the ordinary case so the element is skipped rather than rendered
empty. `outcome` is a bare string printed as text: no verdict colour, since a rejected webhook
is not a gate refusal.

## The buyer area

Three routes under `/buyer`, for the *other* role: `/buyer` creates a mandate,
`/buyer/mandates` lists and revokes them, and `/buyer/api-keys` mints and revokes the buyer's
own platform keys. Pages are one-line pass-throughs; the screens live in `components/buyer/`.

`app/buyer/layout.tsx` is an auth **and role** guard — the same client-side `GET /core/login/`
as the dashboard's (the `sessionid` cookie belongs to the API origin, so nothing on the server
can ask), plus `user_role !== 3` → `/dashboard`. `app/dashboard/layout.tsx` bounces a buyer the
other way, and both re-check on every mount because neither can rely on the other having run.
It provides `SessionContext` for symmetry with the dashboard, but no buyer screen consumes it
yet — `user.merchant` is always `null` for a buyer, so there is nothing on it to want.

`components/buyer-sidebar.tsx` is the rail: one flat `NAV`, one "Menu" group, no badge fetch
and no `KillSwitch` (both are store concepts). `isActive` is an **exact** `pathname` match,
which is correct only while no route nests under one of the three. Note this file uses **no
semicolons**, unlike everything in `components/buyer/`.

`/buyer/api-keys` is `components/buyer/api-keys-screen.tsx` — one file, not the mandates
screen's form/list pair, because those split to serve two routes and this serves one. Its
`hooks/use-api-keys.ts` follows `use-mandates.ts` exactly (`.then` chains, one shared `busy`
boolean, mutations answering with what landed, refetch rather than splice); the one deviation
is `revoke` branching on `error` — see *API client* for why. Three decisions worth keeping:

- **A blank key name is refused client-side**, though `PlatformApiKeyCreate.name` is optional
  on the wire. A key list is a list of prefixes; without a name there is nothing to tell two
  of them apart by when the time comes to revoke one.
- **Revoked keys stay listed.** `revoked_at` on the list row means the DELETE soft-revokes, so
  the row flips to a Revoked pill and loses its button rather than vanishing — same as a
  revoked mandate. Two states, so the pill is a ternary and not `MandateList`'s `STATE` map.
- **No MCP endpoint address on the screen.** A key is only useful against an endpoint, but
  `Login.merchant` is `null` for a buyer and nothing in the API reports a platform-wide MCP
  URL. Printing a guessed one is worse than printing none — add it when an endpoint reports it.

The two panels sit side by side in the `lg`/`xl` grid the ledger, products and Razorpay screens
use — list at `minmax(0,1fr)`, create form as the fixed 340/420px rail, since the rows need the
width and a one-field form does not. `items-start` on that grid is load-bearing: without it the
short form panel stretches to the list's height and leaves a void under its button. The list is
first in the DOM, so below `lg` it stacks above the form — which is why its empty state points
downward at it.

The create form is this screen's **one dark panel** (§1 rule 5), on the Razorpay screen's exact
recipe: `bg-navy-900` / `text-navy-050`, `--navy-200` for secondary text, `bg-navy-200/12` for
the field surface, and an `ON_NAVY` button (`bg-navy-200 text-navy-900`) because `Button`'s
`variant` knows nothing about a dark ground. That is why `FIELD`/`INPUT`/`LABEL` here are *not*
byte-identical to `mandate-form.tsx`'s — same three roles, restated for navy. `PanelHeader`
needs no variant: its title inherits colour, and only its optional `meta` is `text-muted-ink`,
which this panel does not pass.

`mask()` in `components/dashboard/parts.tsx` ("first 8 … last 4") is shared by this screen's
issued-key dialog and `mandate-form.tsx`'s issued-token dialog — the two things this app hands
over exactly once. It was promoted out of `mandate-form.tsx`, the same move `callerOf()` and
`moment()` made. The masked value is display only; the whole credential leaves solely through
`CopyButton`, so a screenshot or a shoulder gets nothing.

## Theme

Dark mode was wired at the token layer long before anything could reach it. It now has a
switch, and it is not `next-themes` — that dependency was removed on purpose (see
Notifications below), so re-adding it would reopen the sonner problem.

The whole mechanism is the `.dark` class on `<html>`:

- `app/layout.tsx` runs a blocking inline `<script>` in `<head>` that applies the saved
  theme before first paint. Without it a dark-mode reload flashes the light page. `<html>`
  carries `suppressHydrationWarning` because that script mutates the class list before React
  hydrates.
- `components/theme-toggle.tsx` flips the class and writes `localStorage.theme`. It reads
  the class through `useSyncExternalStore` + a `MutationObserver` rather than mirroring it
  into state — the DOM is the source of truth (the inline script may have set it already),
  and it is the one hook that hydrates a browser-only value without either a mismatch or a
  `react-hooks/set-state-in-effect` error.

Never branch on the theme in markup. `.dark` redefines the same role tokens (DESIGN.md §1
rule 4); if a component needs a `dark:` variant to look right, the token bridge is wrong.

## Design system

`DESIGN.md` is binding, and it is now implemented rather than aspirational:

- `app/munim-theme.css` — navy scale + warm sand, role tokens, the `.dark` swap, and
  the `@theme` blocks that turn the spec's type/radius/spacing scales into utilities.
- `app/globals.css` — maps shadcn's semantic names (`--card`, `--primary`, `--sidebar-*`,
  …) onto those role tokens. This bridge is why `components/ui/*` is on-brand with a
  single edit inside it (`button.tsx` → `rounded-full`, since §6 makes every button a
  pill). Put only `var()` here, never a literal colour.
- `app/layout.tsx` — Outfit, one variable font, no second typeface.

Use the generated utilities, not arbitrary values: `text-card-title`, `text-eyebrow`,
`bg-panel-2`, `text-muted-ink`, `border-rule`, `rounded-md`, `gap-panel`, `shadow-card`.
`rounded-2xl/3xl/4xl` are clamped to the 32px ceiling so an off-scale radius cannot
re-enter through an existing shadcn class. `DESIGN.md` §9 lists the full mapping and
three name reconciliations — chiefly that **`--muted` is secondary *text* here while
shadcn's `muted` is a *surface*** (`text-muted-ink` vs `bg-muted`).

Body text defaults to 14px/1.6, not 16px. `p` carries a 660px measure globally; override
with `max-w-none` where a panel must fill.

Token *values* are imported verbatim from the Claude Design project `6b9dc3ec`
(`munim-theme.css`). Read them from there — via the DesignSync tool after `/design-login` —
rather than deriving them from DESIGN.md's prose, and don't nudge a hex toward the navy
scale: several role values sit deliberately between scale steps. Four names are
reconciled rather than copied (`--muted`, `--destructive`, `--color-accent` → `--accent-ink`,
and the `shadow-card` utility); DESIGN.md §9 lists them.

The create-next-app template that used to sit in `app/page.tsx` is gone — that file is now
a `redirect("/dashboard")` — so every rendered route is on-system.

## API client

`src/client/` is generated by openapi-ts (`openapi-ts.config.ts`, schema from the Django
app) and is **never hand-edited** — it's eslint-ignored for that reason. `lib/api.ts` holds
what the generator can't know: `credentials: "include"` (auth is a cross-origin `sessionid`
cookie, so fetch's `same-origin` default would silently drop it) and `baseUrl` from
`NEXT_PUBLIC_API_URL`. It also exports `basicAuth()` — `POST /core/login/` takes HTTP Basic
in a header, not a JSON body — and `describeApiError()`. `API_BASE` is exported separately
because `EventSource` is not a hey-api call and cannot read the client's config.

`describeApiError()` walks the error's leaves rather than matching the three shapes the schema
advertises, because those are only the ones the backend hand-builds. `base/exceptions.py` also
passes DRF and Django validation errors through **raw**, and neither matches: a rejected rule
config arrives as `400 {"config": {"amount_paise": ["Ensure this value…"]}}`, and a Django
`ValidationError` as `409 {"msg": [...]}` — an *array*. Reading only `typeof msg === "string"`
turned every field-level complaint into "Something went wrong", which on the policy screen
meant a merchant was told nothing about the value they had just typed.

Regenerate with `bun run openapi-ts`, which needs the backend up on `https://localhost:8000`.
Both scripts set `NODE_TLS_REJECT_UNAUTHORIZED=0` for the self-signed dev cert.

Remaining schema gap: `GoogleAuth` is `{ id_token }` only, so the merchant/buyer choice
cannot reach `/core/google/`. Google sign-ups get whatever role the Django view defaults to.

`Login.merchant` is `Merchant | null` — `{domain, business_name, is_payment_ready,
webhook_url, mcp_url}`, and `null` for a buyer. It only types correctly because
`LoginSerializer.get_merchant` carries an `@extend_schema_field`; a bare
`SerializerMethodField` regenerates as a bare `string`. Only `domain` is read from it, by the
ledger screen and `ExportChainButton` — the products screen gets the same fields from
`GET /ingest/` and the Razorpay screen from `GET /core/razorpay/`, both of which answer a
whole screen in one call and so make the session's copy redundant. Note every field on
`Merchant` is *optional as well as* nullable, so `domain` needs `?.` and a fallback both.

`GET/POST/DELETE /core/api-keys/` is Munim's **own** platform keys, not Razorpay credentials —
a buyer mints them for their own tools to reach the platform-wide MCP endpoint. They are wired
now, at `/buyer/api-keys`; see *The buyer area*. Three things about them: the GET answers a
**bare array**, not the `{count, next, previous, results}` wrapper the orders/products/ledger
lists use, so there is nothing to page; `PlatformApiKeyIssued.key` is returned exactly once at
creation and is never retrievable again (only its hash is stored), which is what the screen's
copy-now-or-lose-it dialog exists for; and `deleteCoreApiKeys` has no generated `Responses`
type at all — its success payload types as `unknown`, so `use-api-keys.ts` branches on `error`
where every other mutation in the repo branches on `!data`. On `PlatformApiKey` only `prefix`
and `created_at` are guaranteed: `uuid` and `name` are optional and `last_used_at` /
`revoked_at` are optional *and* nullable, so the `uuid` guard before a path param is
load-bearing, not defensive noise.

`POST /core/register/` returns the account, not a session, so the page follows a successful
register with `POST /core/login/` using the same credentials.

## Notifications

Every error, success and pending state goes through Sonner — there is no inline error copy
left in any page. The single `<Toaster />` lives in `app/layout.tsx`; a second one anywhere
duplicates every toast. `components/ui/sonner.tsx` is edited away from the registry
default: `useTheme()` from `next-themes` is gone (nothing sets a theme here, and its
`"system"` fallback darkened toasts on a light page), so `theme` is pinned to `"light"` and
the base colours come from `--popover`/`--border`, which already flip with `.dark`.
`richColors` is on **by explicit request**, and is the one sanctioned exception to
DESIGN.md's no-red/green rule: `toast.error` red, `.warning` amber, `.success` green,
`.info` blue. It only paints typed toasts, so reach for a typed call rather than a bare
`toast()` unless a message really has no verdict. A multi-request flow (register → login)
reuses one `toast.loading` id so the stages update one toast instead of stacking.

## Skills

`.agents/skills/` (symlinked into `.claude/skills/`) holds third-party design skills
installed via `npx skills add`. They are not project convention and several contradict
each other and the repo — pick one per task, deliberately.
